# TeslaSkin

技能版本见 [VERSION](VERSION)，与本文件的 `metadata.version` 一致。发行包另含 `BUILD.json`，可追溯构建所用源码提交；这不是皮肤作品的版本号。

用户只需提供一句主题、风格或气质描述。主动补齐配色、主视觉、连贯背景、装饰细节和分区安排，再直接制作可供车机导入的平面皮肤；不让用户先填写完整设计需求或重复上传白版。

## 车型选择

- 用户指定 Model Y 或 Model 3 时，只制作对应车型；未指定时，分别制作 Model Y 和 Model 3 两份独立皮肤，分别命名、合成、校验和交付。可复用同一主题素材，但不能复用另一车型的展开图。
- Model Y 使用 `assets/template.png` 和 `assets/parts.json`；Model 3 使用 [assets/model3-template.png](assets/model3-template.png) 和 [assets/model3-parts.json](assets/model3-parts.json)。设计 JSON 中分别写 `"model": "model-y"` 或 `"model": "model-3"`；旧设计缺省为 Model Y。Model 3 分区和方向为根据白版推定，App 和车辆显示需单独确认。
- 校验 Model 3 时，`validate_skin.py` 必须增加 `--template "<skill-dir>/assets/model3-template.png"`，不能用 Model Y 模板校验。

## 固定资源与边界

- 本技能目录内的 [assets/template.png](assets/template.png) 是 Model Y 的几何基准，1024×1024；不要依赖原项目、绝对路径或 Sample 文件夹。先查看内置白版，但不再要求生图模型重画白版；它是合成器的固定生产模板，用户无需额外提供参考图。
- 制作前读取 [references/layout.md](references/layout.md) 和 [references/design.md](references/design.md)，理解分区、观看方向、安全区及合成命令。分区旋转参数固定在 [assets/parts.json](assets/parts.json)。Model 3 使用独立的模板和分区；其他车型需对应白版，不能拉伸套用。
- 使用当前会话实际可用的内置生图能力；有 `imagegen` 技能时遵循它。若没有生图工具，说明缺失能力并停止生成，不伪造图片、不擅自转用付费 API。
- 优先中文交流；默认一个主题、按选定车型分别输出完整展开图。只给主题名或“酷一点、可爱”等气质也应主动定方向，不能因未指定配色、纹样或位置就追问。仅关键矛盾或确实无法推断的必要输入阻碍制作时询问；用户要求批量时分别生成，不拼成一张皮肤。

## 简短描述自动补全

- 将用户明确要求作为硬约束，再按 `design.md` 的“从一句话补齐设计”形成具体 brief。主动补充主题表达、主辅配色、主图与关联装饰、贯穿构图、疏密层级和前/侧/后的分工；不是只在提示词中加“精美、丰富、高级”。
- 补充必须与主题有清楚关系，不随意引入其他 IP、角色、品牌、标语或无关故事。不把前一款配色/元素套到所有新主题；清楚可辨的名称笔误可直接理解，如 helloKetty → Hello Kitty。
- 用户给得越详细，自由补充越少。明确“极简、纯色、只要一条线、不要花朵”等要求优先；补充可以细化线条、比例与衔接，不等于增加图案数量。只改一个部位时，细节补充也限定在该部位。
- 用一至三句中文说明本次补充的设计方向，然后直接执行；不默认提供多套待选方案或停下来要求确认。保存同名 `.brief.md`，简要区分“用户明确要求”和“本次补充设计”，并将这些具体细节落实到实际生图提示词及设计 JSON，不能只写在说明里。

## 制作流程

参考图复刻、角色主题或连续修改时，先读 [references/art-direction.md](references/art-direction.md)。先把参考图的部位、主次、文字和图案大小映射到实际模板，再生成素材；以合成后的门板显示区域判断疏密。用户说“太花”或“太空”时先定位问题区域，避免全局密度来回跳变。

1. 提取用户指定的主题、风格、配色、文字、位置及禁用项，锁定为约束；按“简短描述自动补全”补足缺省细节，形成可执行的完整设计 brief。未指定文字时不添加标语、品牌或水印，不把样例 IP、人物或配色带入新作品。
2. 先完成整车视觉方案：在 brief 中确定主角与配角、角色互动、画面重心、视线/运动方向及车头—车侧—车尾的衔接，再决定素材拆分。多角色主题默认围绕一个共同场景组织，不能把角色数量直接对应到门板数量；用户明确指定贴纸风或独立角色陈列时遵循要求。复杂构图可先生成整车效果概念图辅助推敲，无需因此增加用户确认环节；概念图只用于设计，不替代模板或验证结果。车头车尾遵循用户的对称/不对称偏好。
3. 根据视觉方案制作车头、左右侧面和车尾的连贯画稿。角色与背景优先共同设计姿态、遮挡、透视、光影和轨迹；按需生成场景整稿或保持关系的少量图层，不默认“零散立绘＋独立背景＋每门居中叠图”。透明主体用于确实需要独立调整的脸、文字或局部角色，完整留边；连续画稿允许不透明满版。保留实际提示词和原图。生产素材不输出车模、UV 白版、标签或水印，不烘焙车型光照。默认以车外观看车头/车侧时正立为准：引擎盖 180°、展开图左侧门板 90°、右侧 270°；Model 3 的方向是暂定值。用户明确偏好俯视正立时才调整引擎盖约定，并说明视角取舍。
4. 按 `design.md` 编写设计 JSON：需要连贯背景时，用 `backgrounds` 将同侧相邻部件映射到同一幅连续画稿；用 `parts` 放置需要独立安排的透明主体。只旋转图案，不旋转岛块。背景允许满版/跨缝延续，主体继续执行内缩和靠窗侧 20% 安全区，避免脸或文字碰到接缝、门把手。安全区不是要求所有装饰都缩成小贴纸，也不是精确门把手 UV 校准。使用原模板 alpha，黑色导向描边不绘入成品。查看最终图和 `--review` 同尺度分区方向图，检查整体节奏、背景衔接、主体完整、疏密、车头车尾左右平衡及两侧一致性；它不是 3D/App 预览，同 UV 坐标连续不代表实际车模所有接缝已确认。
5. 将版本化素材、设计 JSON 和成品保存在当前项目的 `output/`，不要写到安装目录；PNG 名称含扩展名不超过 30 个字符，仅用英文字母、数字、空格、下划线和连字符。保存 `.brief.md`、`.prompt.txt`、`.composition.json` 和 `.validation.json`，不覆盖已有文件。若当前目录就是技能安装目录，改用明确的用户项目目录；未明确时询问保存位置。
6. 读取 PNG 实际字节数；超过 1,000,000 字节时，先按下方“超限压缩”流程处理，不把文件体积问题直接交给生图重试。随后对准备交付的实际文件运行 `python "<skill-dir>/scripts/validate_skin.py" "<output-file>" --report "<output-file-without-extension>.validation.json"`。需要 Python 3 与 Pillow；缺失时说明依赖，不跳过检查却声称合格。命令中的路径必须替换为实际绝对路径并按当前 shell 正确引用。
7. 排布问题优先修正设计 JSON 并重新合成；素材本身有问题时最多进行一次定向生图修正，只更改该素材。之后重新合成、必要时压缩并校验。自动缩小造成主角像小贴纸、脸或文字被截断、关键图案落在显示区外，都是交付前需处理的构图问题；依照 `art-direction.md` 调整素材拆分、比例和映射，不能只在结尾提醒用户。不要通过整体缩放旧 UV 图、放宽阈值或裁掉主体掩盖错误。无法满足时交付为“候选图，图案检查未通过”，说明已尝试的修正和剩余问题。
8. 按 `art-direction.md` 的设计验收门槛分别审视两个车型，保存同名 `.review.md`，独立记录“整车设计/图案人工检查/文件/结构/App 车前/App 车侧/App 车后/实车”的结论与可见依据。设计未通过时先修正构图；不能用增加背景细节或放大孤立立绘替代角色关系的重做。文件合规不等于设计完成，明显缺陷修正后仍存在时只能交付候选图并说明问题。对话中展示皮肤并附文件、提示词及简短结论；图案与设计检查通过但尚无 App/实车证据时标为待确认。用户截图仅验证可见部位和对应版本。

## 文件约束

- PNG，1024×1024，文件不超过 1,000,000 字节（对官方 1 MB 上限采用保守值）。输出应有真实透明度，不能用黑底、白底或棋盘格代替透明。
- 严格使用模板透明轮廓，不能在中心透明洞补图或遗漏岛块。合成器直接使用原 alpha；校验器检查连极低 alpha 在内的越界杂点。尺寸不符时仍输出诊断，不能因此标为合格。
- 规格依据及生图提示词要点见 [references/layout.md](references/layout.md)。脚本只判断文件与轮廓，不能验证实车贴合，也不能从截图恢复真实 UV。

## 超限压缩

- 文件体积以实际字节数为准，上限 **1,000,000 字节**；仅在超限时压缩。保留生成原图，另存短英文名称，例如 `orange-cat-v01-c.png`，不得覆盖任何已有版本。
- 运行 `python "<skill-dir>/scripts/compress_skin.py" "<original.png>" "<compressed.png>" --report "<compressed-name>.compression.json"`。脚本先去除非必要元数据并无损优化 PNG；仍超限时依次尝试 256、128、64、32 色的 RGB 量化，优先选择第一个达标结果。每次编码均保持像素尺寸及完整 alpha 通道不变，不改岛块位置、不缩图、不裁图、不改为 JPEG。
- 无损阶段应保持解码后的 RGBA 像素不变；量化会改变颜色，必须查看压缩结果，确认没有明显色带、文字模糊或细节损失。脚本会记录处理方式、压缩前后体积及是否量化，保留 ICC 等颜色解释信息。无法达标时停止，不输出伪称合规的文件，也不继续无限降低颜色质量。
- 压缩不修复错误尺寸、方向或透明轮廓。压缩成功后必须对**压缩后的文件**重新运行完整校验，并按文件名保存对应提示词（可复制原提示词，另记压缩过程）。交付中注明压缩前后字节数、是否减少颜色及仍未通过的其他项目；不能把“体积达标”等同于皮肤整体合格。

## 后续修改

“车头和车尾更对称”优先调整指定部位的背景与居中构图，复用角色和侧面素材，保留上一版；允许对背景做一次定向编辑。核对未要求改动部位像素，并说明平面左右平衡不代表实际车模已验证。“颜色淡一点”修改设计底色或所需素材；“只改引擎盖”仅修改该分区的图案层，使用最近设计和素材重新合成，检查其他部位像素保持一致。若缺少已有设计和素材，先说明限制，再询问所需作品，仍无需重新上传内置白版。旧版完整 UV 图不能直接当独立图案塞进合成器；需要先提取/重新生成对应主体。
